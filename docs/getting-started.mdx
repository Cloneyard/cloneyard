---
title: Getting started
description: Build Cloneyard from source, start its daemon, add a git repo as a project, log in to Claude Code and run a first clone on them.
---

## Requirements

- [rustup](https://rustup.rs): the first build installs the toolchain pinned in `rust-toolchain.toml`.
- `git` on the daemon's `PATH`, which finds the top level of a repo you add and makes the checkouts of clones.
- Claude Code on the `PATH` of the terminal where you add an account, and on the daemon's, which runs clones.
- Linux 5.13 or newer with Landlock, which the [sandbox](/cloneyard/sandbox) of clones needs.
- `XDG_RUNTIME_DIR` set to an absolute path, as a systemd login session does.

<Aside type="caution">
Without an absolute `XDG_RUNTIME_DIR`, both `cy daemon` and `cy ping` stop with `error: XDG_RUNTIME_DIR is not an absolute path, and the daemon socket lives there`.
</Aside>

## Build and run

<Steps>

1. Build the binaries:

   ```bash
   git clone https://github.com/Cloneyard/cloneyard.git
   cd cloneyard
   cargo build --release
   ```

   The build puts `cloneyard` and its short alias `cy` in `target/release/`.

2. Start the daemon in one terminal:

   ```bash
   ./target/release/cy daemon
   ```

   It runs in the foreground until Ctrl+C or SIGTERM. Its socket is in `$XDG_RUNTIME_DIR/cloneyard/`. The node database is in `$XDG_DATA_HOME/cloneyard/`, or in `~/.local/share/cloneyard/` when `XDG_DATA_HOME` isn't an absolute path.

3. Ping it from a second terminal:

   ```bash
   ./target/release/cy ping
   ```

   ```text frame="terminal" title="cy ping"
   cloneyard 0.0.1, node 01M78NQX36NZR72XQAPW7YA49H, round trip 0.08 ms
   ```

   The node id stays the same after the daemon restarts.

4. Add your copy of the repo as a project:

   ```bash
   ./target/release/cy project add .
   ```

   ```text frame="terminal" title="cy project add ."
   added project cloneyard (01M7R5WVZ8JTATRW81TQGTBJHD)
   ```

   A path inside a repo adds the repo at its top level. The project takes the name of the repo's directory, or the one given with `--name`.

5. List the projects:

   ```bash
   ./target/release/cy projects
   ```

   ```text frame="terminal" title="cy projects"
   cloneyard  /home/you/cloneyard
   ```

   Adding a repo that is already in a project, or a path outside a git working tree, fails with a message that names the path.

6. Log in to Claude Code as an account:

   ```bash
   ./target/release/cy account add personal
   ```

   ```text frame="terminal" title="cy account add personal"
   Hello there.
   added account personal (01M84Z9N24BDSV22G338Z4YTBT)
   ```

   Before these lines, `claude auth login` opens your browser to sign in. It logs in to a config directory of the account's own, `accounts/personal/claude` in the data directory, never to `~/.claude`, and Cloneyard marks Claude Code's theme picker and welcome screen as seen there. A taken name fails before the login, and a cancelled or failed login adds nothing.

7. List the accounts:

   ```bash
   ./target/release/cy accounts
   ```

   ```text frame="terminal" title="cy accounts"
   personal  claude-code  /home/you/.local/share/cloneyard/accounts/personal/claude
   ```

8. Run a clone on the project and the account:

   ```bash
   ./target/release/cy clone run --project cloneyard --account personal "Say pong"
   ```

   ```text frame="terminal" title="cy clone run --project cloneyard --account personal"
   CT-0001
   ```

   The clone is a headless `claude -p` in a checkout of its own: a `git clone --shared` of the repo's last commit on branch `cloneyard/ct-0001`, which never writes to the repo. Your uncommitted changes stay out of it. Claude Code keeps the clone's answer in its transcript in the account's directory.

   The clone runs in a [sandbox](/cloneyard/sandbox): it can't read your `.env`, your SSH keys or the repo itself, and it writes only in its own directory. Claude Code's default permission mode also denies its edits and commands, unless the repo's own `.claude/settings.json` allows them.

9. List the clones:

   ```bash
   ./target/release/cy clones
   ```

   ```text frame="terminal" title="cy clones"
   CT-0001  cloneyard  personal  headless  done
   ```

   A clone is `working` until Claude Code's answer ends its turn, then `done`, or `error` with the reason. While it runs, its [hooks](/cloneyard/hook-events) can make it `blocked` or `idle`. One that is still running when the daemon stops ends `error`.

10. Show a clone, by its handle or as `ct-1`:

    ```bash
    ./target/release/cy clone show CT-0001
    ```

    ```text frame="terminal" title="cy clone show CT-0001"
    handle    CT-0001
    id        01M8F3K2Q9V7T4R6N5X1C0B8ZD
    project   cloneyard
    account   personal
    mode      headless
    state     done
    sandbox   on
    branch    cloneyard/ct-0001
    checkout  /home/you/.local/share/cloneyard/clones/01M8F3K2Q9V7T4R6N5X1C0B8ZD/checkout
    session   5f0c8d2e-7b1a-4c3e-9d6f-2a8b4e1c7d90
    event     SessionStart      12s ago
    event     UserPromptSubmit  12s ago
    event     Stop              9s ago
    event     SessionEnd        9s ago
    ```

    The last lines are the clone's last 10 hook events, each with its tool, if it has one, and its age.

    `cy clone stop CT-0001` ends a clone that is still running and prints `stopped CT-0001`.

    <Aside type="caution">
    Don't run git or an IDE in a clone's checkout: its `.git`, with its config and hooks, belongs to the clone.
    </Aside>

</Steps>
